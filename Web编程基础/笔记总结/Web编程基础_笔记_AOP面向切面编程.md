**Aspect-Oriented Programming**
### 1. 为什么需要 AOP？（解决什么痛点）

假设你现在正在写后端的 Controller，里面有三个控制硬件的接口：

1. `抓取控制接口 (grab)`
    
2. `底盘移动接口 (move)`
    
3. `获取温湿度接口 (getSensorData)`
    

在最原始的写法里，你的每个接口代码大概长这样：

```Java
public String grab() {
    // 1. 校验 JWT Token（看用户有没有登录）
    // 2. 记录操作日志（谁在什么时间发起了操作）
    // 3. 开启数据库事务
    
    // === 真正核心的业务代码 ===
    System.out.println("向边缘端下发机械臂抓取指令...");
    // ==========================

    // 4. 提交数据库事务
    return "抓取成功";
}
```

**痛点出现了：** 每一个接口里，真正的业务代码只有一两行，但为了保证系统安全和稳定，你得写一大堆跟核心业务无关的“废话”（鉴权、日志、事务）。如果你的项目有 100 个接口，这些代码你得复制粘贴 100 遍。一旦你想修改 JWT 的校验规则，你就得改 100 个地方。

这种每个接口的通用逻辑，在软件工程里叫“横切关注点”。

### 2. AOP 是怎么大显身手的？

AOP 的核心思想非常霸气：**让核心业务专心做自己的事，把那些烦人的琐事全部抽离出来，统一“切”进去。**

有了 AOP 之后，你的核心代码就变得极其清爽：

```Java
public String grab() {
    System.out.println("向边缘端下发机械臂抓取指令...");
    return "抓取成功";
}
```

那么鉴权和日志去哪了呢？你写了一个独立的 **“切面类”**。当程序运行时，AOP 框架会像个幽灵一样，在你调用 `grab()` 方法的**前一瞬间**，自动帮你执行 JWT 校验；在 `grab()` 执行**完之后**，自动帮你打日志。

对业务代码来说，它甚至不知道外层发生了什么，它只管跑自己的逻辑就行了。

### 3.AOP术语

- **JoinPoint (可拦截点) —— “所有可以设卡安检的地方”** 在 Spring 里，你写的每一个 `public` 方法，理论上都可以被 AOP 拦截。这些方法统统叫连接点。
    
- **Pointcut (要拦截点/切入点) —— “你最终决定设卡的地方”** 你不可能每个方法都去拦截。你通过写规则告诉 Spring：“我只拦截头上贴了 `@CheckToken` 注解的方法”，或者“我只拦截 `controller` 包下的所有方法”。这个规则就是切入点。
    
- **Advice (通知) —— “安检员具体要干的活”** 拦截下来之后你要干嘛？
    
    - `@Before`（前置通知）：方法执行前干活（比如校验 JWT）。
        
    - `@After`（后置通知）：方法执行后干活（比如清理缓存）。
        
    - `@Around`（环绕通知）：最强大，方法执行前后都能干活，甚至能阻止目标方法执行（比如发生异常直接返回错误码）。
        
- **Aspect (切面) —— “安检站”** 切入点 + 通知 = 切面。你把“在哪里拦截”和“拦截后干什么”写在同一个类里，这个类头上贴个 `@Aspect`，它就是一个完整的切面了。
### 4. 底层是怎么做到的？（动态代理技术）

你可能会觉得很玄学：为什么我只调用了 `grab()`，它能自动先去跑别的代码？

因为 Spring 偷偷把你原本的那个 Controller **掉包了**。 在项目启动时，Spring 发现你对 Controller 配置了 AOP 切面。它就不会把原始的 Controller 交给程序，而是**在内存里动态生成了一个 Controller 的“替身”（代理对象）**。

当请求打过来时，其实是打在了替身身上。替身在内部先执行了切面的逻辑（鉴权），确认无误后，替身才去调用真正 Controller 里的 `grab()` 方法。
